# 기존 레포 이관 계획 (ssehuun/kis_trading → 목표 설계)

전체 8,690줄 / 54 커밋. **약 5,000줄 재사용, 약 1,500줄 재작성, 약 2,000줄 신규.**

---

## 1. 결론

**새로 짜지 않는다.** 재사용 자산이 크고, 그중 상당수가 만들기 가장 번거로운 부분이다.

특히 중요한 발견: **백테스트와 실전이 이미 동일한 전략 인터페이스를 공유한다.**

| 위치 | 호출 |
|---|---|
| `backtest_manager.py:102` | `self.strategy.update(price)` |
| `last_price_manager.py:395` | `strategy.update(float(candle.close))` |

설계 원칙 1번("백테스트와 실전은 같은 코드를 실행한다")이 이미 지켜져 있다.
이 성질을 깨지 않는 것이 이관의 최우선 제약이다.

## 3. `strategies/` 재작성 이유

### 3.1 데이트레이딩 파라미터로 만들어져 있다

`close_breakout_strategy.py` 기본값:

| 파라미터 | 값 | 함의 |
|---|---|---|
| `stop_loss_pct` | 0.006 (−0.6%) | 확정한 −5%의 1/8 |
| `take_profit_pct` | 0.010 (+1.0%) | 고정 익절. ATR 트레일링과 개념이 다름 |
| `max_hold_bars` | 90 (분봉 90개) | 약 1.5시간. 스윙이 아니라 인트라데이 |
| `cooldown_bars` | 10 | 분 단위 쿨다운 |

값만 바꾸면 되는 문제가 아니다. **고정 익절과 ATR 트레일링은 구조가 다르다.**
트레일링은 최고가와 ATR을 계속 추적해야 하고, 스톱 하향 금지 성질이 필요하다.

### 3.2 전략이 상태를 소유한다 (설계 원칙 3 위반)

```python
self.in_position = False
self.entry_price = None
self.hold_bars = 0
self.cooldown_remaining = 0
```

전략 인스턴스가 포지션 상태를 직접 들고 있다. 문제:

- **재시작하면 상태가 사라진다.** `reset()`은 있으나 복구 경로가 없다.
  청산이 자동인 시스템에서 재시작 후 `in_position=False`가 되면 손절이 발동하지 않는다
- 실제 브로커 잔고와 전략 내부 상태가 갈라질 수 있다. 대조 수단이 없다
- 백테스트 재현 시 상태 초기화 순서에 결과가 의존한다

목표 구조에서는 상태를 DB가 소유하고, 전략은 `(clock, data_view) → 목표`를 반환하는 순수 함수여야 한다.

### 3.3 단일 종목 단위다

`update(close_price)` 는 종목 하나의 종가만 받는다.
`last_price_manager`는 `{symbol: strategy_instance}` 딕셔너리로 종목별 인스턴스를 만든다.

이 구조로는 **"최대 5종목, 균등 20%"를 표현할 수 없다.**
종목 간 슬롯 경쟁, 자본 배분, 신호 경합 스킵은 포트폴리오 레벨 개념이고,
종목별 독립 인스턴스에는 이 정보가 없다.

### 3.4 이관 방식

**폐기하지 않고 참조용으로 남긴다.** 진입 판정 로직(돌파, 추세 필터)은 모멘텀 팩터 산출에
재활용할 여지가 있다. `strategies/legacy/` 로 이동하고 새 `core/`를 별도로 작성한다.

## 4. `backtest_manager.py` 재작성 이유

### 4.1 종가 즉시 체결 — 코드가 스스로 인정하고 있다

`backtest_manager.py:105-108` 주석:

> 시그널 발생 시점은 '봉 완성 시점'이므로, 실제 매매는 '다음 봉 시가' 또는 '현재 봉 종가'로
> 가정해야 함. 여기서는 편의상 현재 봉 종가로 즉시 체결된다고 가정 (Slippage 미고려)

이건 look-ahead다. 종가를 보고 판단한 뒤 그 종가에 체결하는 것은 실전에서 불가능하다.
설계에서 확정한 **"진입은 다음 개장 시가, 손절은 시가 체결"** 과도 맞지 않는다.
갭하락 시 손절이 −5%에 체결되는 것으로 계산되어 **성과가 실제보다 좋게 나온다.**

### 4.2 증권거래세 미반영

`backtest_manager.py:187` 주석:

> 매도 시에는 세금도 고려해야 하나 일단 수수료만 적용

`fee_rate` 기본값 0.00015(0.015%)만 적용된다.
국내 주식은 **매도마다 증권거래세**가 붙고, 스윙 전략에서 이건 무시할 수 없는 크기다.
설계 문서에서 "회전율을 낮게 유지하는 것이 전략 성패보다 선행 조건"이라고 한 근거가
이 비용이며, 그것이 백테스트에 빠져 있으면 회전율 판단 자체가 불가능하다.

### 4.3 단일 종목 · 전액 투입

`backtest_manager.py:159`:
```python
quantity = int(self.cash / (price * (1 + self.fee_rate)))  # 수수료포함 최대 매수 수량
```

**현금 전액을 한 종목에 넣는다.** 5종목 균등 20%를 표현할 수 없다.
포트폴리오 개념, 슬롯 관리, 종목 간 자본 배분이 없다.

### 4.4 그 외 누락

- D+2 결제 제약 없음
- 상장폐지 종목 처리 없음 (생존 편향)
- `ingested_at` 기준 재생 개념 없음 (이벤트 소스가 없으므로 당연)
- 워치리스트 스냅샷 사용 안 함 (단일 종목이므로 불필요했음)

### 4.5 재사용할 부분

`_calculate_metrics`, `utils/backtest_report.py`(255줄, 요약 출력·전략 비교·플롯 저장)는
그대로 쓸 수 있다. **체결 엔진만 교체하고 리포팅은 유지한다.**

## 5. 설계 변경: SQLite → PostgreSQL 유지

설계 문서 6.4절에서 SQLite를 권했으나 **철회한다.**

이미 PostgreSQL + SQLAlchemy로 971줄이 구축되어 있고, upsert(`ON CONFLICT`) 패턴이
전반에 쓰이고 있다. SQLite로 옮기는 비용이 얻는 이득보다 크다.

**변경되는 사항:**

| 항목 | 기존 계획 (SQLite) | 수정 (PostgreSQL) |
|---|---|---|
| 백업 | 온라인 백업 API `.backup` | `pg_dump` + 오브젝트 스토리지 업로드 |
| VM 사양 | 1vCPU / 1GB | Postgres 상주 시 **2GB 권장** |
| 배치 방식 | 파일 | VM 내 로컬 인스턴스 또는 관리형 DB |

**여기서 트레이드오프가 하나 생긴다.** 관리형 Postgres는 월 비용이 붙고, VM 내 자체 호스팅은
비용은 없지만 VM 장애 시 DB까지 함께 잃는다. "최대한 싸게"라는 요구를 감안하면
VM 내 자체 호스팅 + `pg_dump` 정기 업로드가 합리적이나, 결정이 필요하다.

## 6. 재사용 시 반드시 확인할 3가지

이관 전에 검증해야 하는 항목. 통과하지 못하면 해당 모듈도 재작성 대상이 된다.

1. **`last_price_manager`의 분봉 집계 경계 처리** — 봉 완성 판정이 정확한지.
   미완성 봉을 종가로 넘기면 청산 판정이 매 초 흔들린다
2. **`data_collector`의 수정주가 처리** — `daily_candles`에 `adj_factor`가 없다.
   액면분할·유상증자 소급 반영 여부를 확인해야 모멘텀 점수가 신뢰 가능하다
3. **`auth.smart_sleep`의 실제 유량 한도** — 워치리스트 50종목 + 보유 5종목을
   1분 주기로 조회할 때 한도 내에 들어오는지 실측

## 7. 수정된 개발 순서

기존 문서(02번)의 순서를 레포 현황에 맞게 조정한다.

| 단계 | 작업 | 검증 |
|---|---|---|
| **0** | 레포 클론, 로컬 실행 확인, 6절 3가지 검증 | 기존 메뉴 1~6번 정상 동작 |
| **1** | DB 스키마 확장 (`events`, `llm_judgments`, `positions`, `orders`, `fills`, `approvals`) | 마이그레이션 후 기존 기능 무영향 |
| **2** | **공시 수집기 신규** (`data/dart.py`) | 하루치 전종목 공시 적재, 재실행 멱등, 잠정/확정 정규화 |
| **3** | `universe_manager` → 모멘텀 + 히스테리시스로 교체 | 일별 스냅샷 저장, 같은 날 재실행 시 동일 결과 |
| **4** | `core/` 신규 작성 (`exit_rules`, `gate`, `diff`, `strategy`) | 순수 함수 단위 테스트, 스톱 하향 금지 성질 |
| **5** | 백테스트 엔진 교체 (체결 엔진만. 리포팅 재사용) | 시가 체결·증권거래세·D+2·5종목 포트폴리오 반영, look-ahead 테스트 통과 |
| **6** | LLM 판단 계층 신규 | 동일 입력 2회 → 캐시 히트로 완전 동일 결과 |
| **7** | `order_manager` 재작성 (멱등 키 추가) | 같은 키 재전송 시 중복 체결 없음, 재시작 후 미체결 복구 |
| **8** | 텔레그램 알림 + 킬 스위치 | `/kill` 후 진입 차단·청산 유지, `/resume` 복귀 |
| **9** | `reconcile` + 워치독 + 백업 | 강제 종료 후 재시작 시 트레일링 상태 재계산이 원본과 일치, `pg_dump` 복구 리허설 |
| **10** | 실전 (소액, 완전 자동) | 포워드 테스트 로그 축적 |

**2단계를 앞으로 당긴 이유**: 공시 데이터는 오늘부터 쌓아야 한다.
기존 레포에 없는 유일한 데이터 소스이며, 늦을수록 백테스트 가능 기간이 짧아진다.
