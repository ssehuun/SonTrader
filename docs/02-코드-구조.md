# 코드 구조 및 개발 순서 (v1.0)

설계 확정본(`01-요구사항-설계-확정.md`)을 코드로 옮기기 위한 구조 문서.

---

## 1. 구조 원칙 3가지

### 원칙 1 — `core`는 아무것도 모른다

`core/`는 **순수 함수와 데이터 클래스만** 포함한다.
DB, 네트워크, 시각(now), 파일, 로깅에 접근하지 않는다.

이유: 백테스트와 실전이 같은 코드를 실행해야 하는데,
`core`가 `datetime.now()`나 DB를 직접 부르는 순간 그게 불가능해진다.
시각과 데이터는 **인자로 주입**한다.

```
core를 import할 수 있는 것: 없음 (표준 라이브러리 + 수치 계산만)
core를 import하는 것: engine, backtest
```

### 원칙 2 — 부작용은 어댑터 뒤에 격리한다

외부와 접촉하는 모든 것은 인터페이스를 가진다.

| 인터페이스 | 실전 구현 | 백테스트 구현 |
|---|---|---|
| `Clock` | 시스템 시각 | 과거 시각 재생 |
| `Broker` | KIS API | 시뮬레이션 체결 |
| `Notifier` | 텔레그램 | 로그만 기록 |
| `LLMJudge` | API 호출 + 캐시 | **캐시 전용** (미스 시 에러) |

`LLMJudge`가 백테스트에서 캐시 전용인 것이 중요하다.
캐시 미스에 조용히 API를 호출하면 백테스트가 비결정적이 된다. **명시적으로 실패해야 한다.**

### 원칙 3 — 상태 변경은 한 곳에서만

포지션·주문 상태를 바꾸는 코드는 `engine/`에만 존재한다.
전략도 게이트도 상태를 바꾸지 않고 "무엇을 원하는지"만 반환한다.

## 3. 핵심 인터페이스

### 3.1 실행 루프 (공용)

```python
def run_cycle(ctx: Context, deps: Deps) -> CycleResult:
    """1분봉 1틱 처리. 실전과 백테스트가 동일하게 호출한다."""
    target  = strategy.build_target(ctx)      # core — 순수
    target  = gate.apply(target, ctx)         # core — 순수
    orders  = diff.to_orders(target, ctx)     # core — 순수
    return deps.broker.submit(orders)         # 어댑터 — 부작용
```

앞의 세 줄이 순수하므로 그대로 테스트할 수 있고, 백테스트에서 동일하게 재생된다.

### 3.2 Context (전략에 주입되는 읽기 전용 스냅샷)

```python
@dataclass(frozen=True)
class Context:
    now: datetime
    bars: BarView             # 현재 시각까지의 분봉만 노출 (look-ahead 차단)
    watchlist: list[str]      # 그날 저장된 스냅샷
    positions: list[Position]
    new_events: list[Event]   # ingested_at <= now 인 미처리 이벤트
    cash: int
```

> `BarView`가 현재 시각 이후 데이터를 **구조적으로 차단**하는 것이 중요하다.
> 규율에 의존하면 반드시 실수한다. 접근 자체를 불가능하게 만든다.

### 3.3 전략

```python
def build_target(ctx: Context) -> Target:
    """진입 후보와 보유 종목을 합쳐 목표 포트폴리오를 반환."""
```

동작:
1. 보유 종목마다 `exit_rules.check()` → 발동하면 목표에서 제외 (`urgency=IMMEDIATE`)
2. `ctx.new_events` 중 워치리스트 종목만 필터
3. 남은 이벤트를 `LLMJudge`에 전달 → 진입 여부 + 청산조건
4. 슬롯이 남으면 목표에 추가 (`urgency=NEXT_OPEN`)

```python
@dataclass(frozen=True)
class TargetItem:
    symbol: str
    weight: float
    urgency: Urgency        # IMMEDIATE | NEXT_OPEN
    exit_rule: ExitRule | None
```

**`urgency`가 집행 비대칭을 코드로 표현한다.** 청산은 즉시, 진입은 다음 시가.

### 3.4 청산 규칙 (순수 함수)

```python
def stop_level(entry_price, high_water, atr, k) -> int:
    if high_water < entry_price * 1.05:
        return entry_price * 0.95          # 고정 손절
    return max(entry_price,                 # 본전 이동 후 ATR 트레일링
               high_water - k * atr)
```

스톱이 하향되지 않는 성질이 `max`로 자연히 보장된다.
`high_water`는 저장하지 않고 **진입 시각 이후 분봉에서 재계산**한다 (백업 부담 감소).

### 3.5 브로커

```python
class Broker(Protocol):
    def submit(self, orders: list[Order]) -> list[OrderResult]: ...
    def positions(self) -> list[Position]: ...
    def cash(self) -> int: ...
```

`broker_kis`가 책임지는 것:
- 유량 제한 큐잉, 토큰 캐싱 (1일 1회 발급 원칙)
- **멱등 키** — 같은 키의 주문은 재전송해도 중복 체결되지 않음
- 타임아웃 시 "접수 불명" 상태 반환 → 다음 사이클에서 주문 조회로 확인

## 4. 데이터 스키마

```sql
events(event_id PK, symbol, corp_code, event_type, title,
       published_at, ingested_at, raw_json)          -- append-only

llm_judgments(event_id, prompt_version, model,       -- PK: 3개 조합
              verdict, confidence, exit_rule_json,
              rationale, created_at)                 -- 백테스트 재현의 핵심

watchlist_snapshots(date, symbol, score, rank)       -- PK: (date, symbol)

bars_1m(symbol, ts, o, h, l, c, v)                   -- PK: (symbol, ts)
bars_1d(symbol, date, o, h, l, c, v, adj_factor)

orders(order_id PK, idempotency_key UNIQUE, symbol, side,
       qty, order_type, urgency, status, event_id, created_at)

fills(fill_id PK, order_id, price, qty, ts)

positions(symbol PK, qty, avg_price, entered_at,
          event_id, exit_rule_json)                  -- high_water 저장 안 함

approvals(proposal_id PK, payload_json, status, expires_at)
```

- `llm_judgments`와 `watchlist_snapshots`가 없으면 **백테스트를 재현할 수 없다.** 최우선 백업 대상
- `positions.high_water` 부재는 의도적이다 (분봉에서 재계산)

## 5. 개발 순서

각 단계는 **다음 단계의 전제**이며, 검증을 통과하기 전에 넘어가지 않는다.

### 0단계 — 스켈레톤
- **작업**: 디렉토리, `config.py`, `db.py` 스키마, SQLite WAL 설정
- **검증**: 빈 DB 생성 후 모든 테이블 조회 성공

### 1단계 — 공시 수집기 ★ 가장 먼저
- **작업**: `data/dart.py`, `apps/collect.py`
- **검증**: 하루치 전종목 공시가 이중 타임스탬프로 적재.
  재실행해도 중복 적재 없음(멱등). 잠정/확정 실적 정규화 동작
- **왜 먼저인가**: 데이터는 오늘부터 쌓아야 한다. 다른 모든 것의 전제

### 2단계 — 시세 수집 + 모멘텀
- **작업**: `data/prices.py`, `core/momentum.py`, `core/watchlist.py`, `apps/universe.py`
- **검증**: 워치리스트 일별 스냅샷 저장. 히스테리시스로 경계 깜빡임 미발생.
  같은 날짜 재실행 시 동일 결과

### 3단계 — 백테스트 엔진 (LLM 없이)
- **작업**: `core/exit_rules.py`, `core/gate.py`, `core/diff.py`,
  `adapters/broker_sim.py`, `engine/loop.py`, `apps/backtest.py`, `apps/report.py`
- **검증**:
  - 청산 규칙 단위 테스트 (구간별 스톱 레벨, 하향 불가 성질)
  - 거래비용·시가 체결·D+2 반영 확인
  - **look-ahead 테스트**: `BarView`가 미래 봉 접근 시 예외 발생
  - 규칙 기반 더미 신호로 전체 루프 관통
  - `apps/report.py`가 §5.3의 CAGR/샤프/MDD/승률/손익비/평균 보유일/거래
    횟수/총 거래비용 비중을 계산 — 표본 30건 미만이면 경고(§5.1)
- **왜 LLM 없이**: 엔진 버그와 전략 문제를 분리하기 위해

### 4단계 — LLM 판단 계층
- **작업**: `llm/backend.py`(제공자 중립 프로토콜), `llm/anthropic_backend.py`,
  `llm/openai_backend.py`, `llm/judge.py`, `llm/cache.py`, `prompts/v1.txt`
- **검증**: 동일 입력 2회 실행 시 캐시 히트로 **완전히 동일한 결과**.
  백테스트 모드에서 캐시 미스 시 명시적 실패. 캐싱·파싱·fail-closed 검증은
  어떤 `LLMBackend`를 주입해도 동일 — Claude/OpenAI 두 백엔드로 확인

### 5단계 — KIS 어댑터 (조회 전용)
- **작업**: `adapters/broker_kis.py` 조회 부분, `engine/reconcile.py`
- **검증**: 유량 제한 하에서 워치리스트 시세 조회 성공.
  잔고 조회 결과와 DB 포지션 대조 동작. 트레일링 상태 재계산이 원본과 일치
- **`engine/reconcile.py` 구현 내용**: `reconcile(engine, broker)`가 (1)
  `KisBroker.resolve_unknown()`으로 미체결 주문부터 해소하고, (2) 브로커
  잔고(qty·평단가, 원본)와 DB `positions`(진입시각·이벤트ID·청산조건,
  브로커가 모르는 상태)를 종목별로 합쳐 `core.types.Position`을 재구성한다.
  한쪽에만 있는 종목은 재구성하지 않고 `PositionMismatch`로 남겨
  `ReconcileReport.halt=True`를 만든다 — 특히 브로커에만 있는 종목은 청산
  조건을 모르므로 안전하게 관리할 수 없다(01문서 §6.5). `data/positions.py`는
  읽기 전용이다 — 진입 체결 시 이 테이블에 쓰는 코드(`apps/live.py`)는
  아직 없다.

### 6단계 — 텔레그램 + 승인 큐
- **작업**: `adapters/notifier_tg.py`, `engine/approval.py`, `engine/killswitch.py`
- **검증**: 승인/거부 버튼 동작, TTL 만료 처리, 킬 스위치 동작
- **`engine/approval.py` 구현 내용**: `propose()`가 진입 후보를 `pending`으로
  큐에 넣는다 — 같은 event_id로 이미 대기 중인 제안이 있으면 새로 만들지
  않는다(멱등, `build_target()`이 승인 전까지 매 사이클 같은 후보를 다시
  내놓기 때문). `decide()`는 상태가 `pending`인지와 `now < expires_at`인지
  둘 다 확인한 뒤에만 `approved`/`rejected`로 바꾼다 — TTL을 넘긴 결정은
  반영하지 않고 즉시 만료 처리한다(fail-closed). `expire_stale()`은 TTL을
  넘긴 대기 중 제안을 일괄 만료시켜 만료 알림에 쓰인다. `pull_approved()`는
  승인된 제안을 반환과 동시에 `consumed`로 바꾸는 원자적 pop이라 같은
  제안이 두 번 주문으로 전환되지 않는다.
- **`engine/killswitch.py` 구현 내용**: 계좌가 하나뿐이라 전역 온/오프
  단일 행(`kill_switch` 테이블, `id="singleton"`)으로 충분하다. `core/gate.py`가
  청산을 절대 막지 않는 것과 같은 이유로 킬 스위치도 신규 진입만 막도록
  설계했다.
- **`adapters/notifier_tg.py` 구현 내용**: `getUpdates` 롱폴링만 쓴다(웹훅
  없음 — 인바운드 포트를 열지 않는다, 01문서 §6.3). `send_approval_request()`가
  인라인 버튼(승인/거부, `callback_data="동작:proposal_id"`)을 보내고,
  `process_update()`가 콜백을 받아 `engine.approval.decide()`를 호출한 뒤
  `answerCallbackQuery`로 사용자에게 결과를 확인해 준다 — 이미 처리됐거나
  만료된 제안에 대한 콜백은 조용히 무시하지 않고 에러 메시지로 답한다.
  `/kill`, `/resume`, `/status` 명령을 처리한다. `/positions`, `/stops`
  (포지션·스톱 상태 조회)는 봉 데이터가 있어야 트레일링 스톱을 계산할 수
  있는데 이 어댑터는 DB만 알아서, `apps/live.py`가 `Context`를 조립할 수
  있게 될 다음 슬라이스로 미뤘다.
- **`engine/loop.py` 연결**: `run_cycle()`이 게이트를 통과한 목표 중
  "아직 보유하지 않은 종목에 대한 양의 비중"(신규 진입)만
  `engine/approval.py`에 제안으로 올린다 — 보유 종목(청산 포함)은 그대로
  통과해 승인 큐를 타지 않는다(집행 비대칭, 01문서 §1.3). 킬 스위치가
  켜져 있으면 이번 사이클엔 제안도, 이미 승인된 제안의 픽업도 하지
  않는다(승인된 채로 큐에 남아 있다가 킬 스위치가 풀리면 다음 사이클에
  픽업된다). `CycleConfig.require_approval=False`(`apps/backtest.py`가
  사용)면 승인 큐를 건너뛰고 게이트 통과 즉시 주문으로 흘려보낸다 —
  백테스트는 사람이 없어 결정적이어야 하고, 01문서 §2.5의 "자동 전환"과
  같은 스위치이기도 하다.

### 7단계 — 주문 집행
- **작업**: `data/orders.py`(주문/체결 영속화), `adapters/broker_kis.py`(제출·
  잔고 조회·체결 확인부)
- **검증**: 모의투자로 주문 → 접수 확인 → 포지션 반영(`positions()`/`cash()`는
  기존 잔고조회 재사용).
  **같은 멱등 키 재전송 시 중복 체결 없음**(DB UNIQUE 제약이 2차 방어선,
  KIS 호출 전에 UNKNOWN으로 먼저 기록해 크래시-사이 유실도 방지).
  프로세스 강제 종료 후 재시작 시 미체결 주문 복구(`list_unresolved()`가 대상 조회)
- **체결 확인**: `KisClient.get_daily_executions()`(주식일별주문체결조회,
  TTTC0081R/VTTC0081R, 3개월 이내)로 `KisBroker.resolve_unknown()`이
  SUBMITTED/UNKNOWN/PARTIAL 주문을 조회해 FILLED/PARTIAL/REJECTED/CANCELLED로
  확정한다. 이 API는 개별 체결이 아니라 누적 체결수량·평균단가만 주므로
  `set_fill_snapshot()`으로 매번 스냅샷을 교체한다(append 아님).
  `broker_order_no`(ODNO)가 없는 주문은 이 API로 특정할 수 없어 건너뛴다 —
  사람이 KIS 앱/HTS에서 직접 확인해야 한다.
  `resolve_unknown()`은 언제 호출할지 스스로 정하지 않는다 — 5단계
  `engine/reconcile.py`가 기동 시점에 호출한다(재시작 복구).
  3개월 이전 체결(CTSC9215R/VTSC9215R)은 다루지 않는다(자가 매매 상태
  확인용이라 항상 최근 주문만 조회하면 됨).

### 분봉 수집기 (번호 없음 — `apps/live.py` 준비 과정에서 발견한 공백)

01문서 §2.2 "엔진은 1분봉만 소비한다"를 채우는 실시간 수집원. 원래
계획에는 번호가 매겨진 단계가 없었다 — `data/prices.py`가 일봉만
수집하는 채로 남아 있었고, `apps/live.py`를 준비하다 이 공백을 발견해
이번에 추가한다.

- **작업**: `adapters/live_ticks.py`(원시 메시지 → `Tick` 파싱, 심볼별
  1분 집계 — 순수, 네트워크 없음), `adapters/live_ws.py`(웹소켓 연결·
  재연결), `auth.py`의 `ApprovalKeyManager`(웹소켓 접속키 캐시),
  `data/live_bars.py`(완성 봉 저장), `stock_candles_1m` 테이블
- **API**: 실시간-003(`H0STCNT0`, 국내주식 실시간체결가)과
  실시간-000(`/oauth2/Approval`, 접속키 발급) — 둘 다 문서(docs/api/*.xlsx,
  로컬 전용)의 예제로 필드 순서·개수를 검증했다
- **동기 코드 안에 asyncio를 격리**: 나머지 시스템(`KisClient`, `run_cycle`,
  `data/*`)은 전부 동기다. 이 규모(계좌 1개, 워치리스트 ≤50종목)에서
  전체를 비동기로 바꿀 이득이 없다고 판단해, 웹소켓 수신만 별도
  스레드에서 자체 이벤트 루프로 돌리고 나머지는 그대로 둔다.
  `LiveTickStream.stop()`은 `Task.cancel()`을 스레드 안전하게 호출해
  블로킹 중인 소켓 수신을 즉시 끊는다.
- **`data/live_bars.py`**: `stock_candles_1d`와 별개 테이블(`stock_candles_1m`,
  PK가 date가 아니라 분 단위 `ts`)이다. `store()`는 upsert다 — 재연결
  직후 마감 처리 중이던 분이 다시 집계될 수 있어, append하면 PK 충돌이나
  중복이 생긴다. `load_recent(symbol, count)`는 `BarView.history()`와
  같은 계약이라 `engine/context.py`가 실시간용 `BarView`를 이 함수로
  조립할 수 있다.
  `LiveTickStream(on_bar=...)`에 `lambda bar: live_bars.store(engine, bar)`를
  넘기는 실제 배선과 `apps/live.py` 조립은 다음 슬라이스다.

## 6. 테스트 전략

| 대상 | 방식 |
|---|---|
| `core/` 전체 | 단위 테스트. 순수 함수라 100% 커버 가능 |
| 청산 규칙 | 구간 경계값 테스트 (+4.9% / +5.0% / 하향 불가) |
| 게이트 | 각 규칙별 차단 케이스 |
| look-ahead | `BarView` 미래 접근 시 예외 |
| 멱등성 | 같은 키 2회 제출 → 주문 1건 |
| 정합성 | 잔고 불일치 주입 → 매매 중단 확인 |

**가장 중요한 테스트는 look-ahead와 멱등성 두 가지다.**
전자는 백테스트를 거짓으로 만들고, 후자는 실제 돈을 잃게 한다.

---

## 7. 하지 않을 것 (YAGNI)

초기 구현에서 **의도적으로 배제**한다. 필요해지면 그때 추가한다.

- 플러그인 로더 / 전략 레지스트리 → 전략은 함수 하나로 시작
- 추상 팩토리, DI 컨테이너 → 진입점에서 인자로 조립
- 마이크로서비스 분리 → 단일 프로세스
- 웹 대시보드 → 텔레그램
- PostgreSQL / Redis → SQLite
- 멀티 브로커 지원 → KIS만
- 실시간 스트리밍 최적화 → 1분봉이면 충분

> 전략을 2개도 안 돌려본 상태에서 플러그인 아키텍처를 만들면,
> 3번째 전략에서 반드시 인터페이스를 갈아엎게 된다.
